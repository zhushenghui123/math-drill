# 数据管线设计 v1（DATA_PIPELINE）

> 定位：把「多本权威书的 OCR 草稿」融合成「高质量、可演进、带出处」的题库资产。
> 本文是设计文档（规划期，零代码）；它与练题系统**只通过 contracts/ 共享契约**，是平行工程不是耦合件
> 决策人的原始判断（本管线的设计出发点，已全部吸收）：
> ① 数据 > 一切（垃圾进垃圾出）② 提取是机械但量大的活 ③ 真技术含量在多源融合 ④ 题库要长期迭代 ⑤ 公开数据集不入池（可作交叉校验参考）

## 1. 管线总览（六段流水线，每段有验收门；LLM 只出现在标 ⓛ 的位置）

```
① ingest 源摄取      书/PDF/教材 → 原始素材（按章分节，frontmatter 记出处）
② segment 题目切割   题干 / 解答 / 易错点 分离（启发式 + 人工抽检）
③ formula 公式规范化 LaTeX 清洗 + 宏展开 + 等价形式标注
④ annotate 知识点标注 ⓛ LLM 提议 → 置信度 → 人工确认（受控词表=68 考点树）
⑤ verify 答案验证    分级门（见 §4）——这是数据侧的 fail-closed
⑥ fuse 融合/去重     跨书同题识别 + 参数化模板识别 + 出处聚合 → bank
```

**纪律**：LLM 永不出现在 ⑤ 的判定链路（N3 的数据侧镜像）。ⓛ 只出现在④，且必经人工确认才算落库。

## 2. 最重要的设计决策：**验证分级门**（verify 的四档）

这是把「垃圾进垃圾出」变成工程问题的全部所在。每道题带**验证状态**，入池规则如下：

| 级别 | 判定方式 | 允许进入 | 备注 |
|---|---|---|---|
| `auto_verified` | **exact.py 等 CAS 代码可判定**（或生成器自产） | ✅ 练习池 | 质量最高，MVP 主力；与练题系统 answer_type 同构 |
| `cross_checked` | ≥2 个独立来源答案一致（OCR+墨题库对拍 / 多书对拍，含参数一致性） | ✅ 练习池（标注 cross） | 需要融合层做参数抽取比对 |
| `human_confirmed` | 决策人读过解析、手工确认答案 | ✅ 练习池 | 解答题的主要通道 |
| `unverified` | 仅 OCR 未复核 | ❌ 只进**审校队列**，不进练习池 | OCR 的默认落点——垃圾进不了池子 |

> 状态机的关键性质：**只能升级、不可降级、不可跳级**（unverified → verified 两条路：auto 或 human；任何已确认题被上游复核降级需记录 ADR）。

## 2.A Provenance（出处追踪）—— 题库能长期演进的免费的纪律

每条题目除了 qa 契约字段（ARCHITECTURE §3.1），携带：

```
provenance:
  book:        书名/作者/版次（受控名著表，防拼写漂移）
  page:        页码（OCR 段落锚点）
  ocr:         [引擎, 版本, confidence]
  segment:     切割判定依据（题号匹配/正则锚点），供回溯原文
  verified:    见 §2 四级状态 + verifier + ts
  relations:   dup_group（同题跨书） / family（参数化同模板） / cross_refs
```

**一票否决的边界（承接既有红线）**：带 provenance 的原始 OCR 数据**永不上传开源仓库**——开源仓里只放「我方生成的题目 xor 用户自备 custom_json」；OCR 资产停在本地/私有备份。

---

## 3. 融合（fuse）的三类判定规则 —— 这里是技术主战场

### 3.1 同题跨书（dup_group）

判据（优先级降序）：① **数学内容指纹**：规范化后的 stem 等价（公式规范化后 hash；公式树不比特串——`\dfrac` vs `\frac` 视为同）② 参数一致（数值题比对全部出现数字集合）③ 结论/答案等价。
处理：合并 provenance（多书互证 → 升 cross_checked）、保一条 canonical（选解析最完整者），其余指向 canonical。

### 3.2 参数化同源（family）——**这是融合最有价值的一步**

同一模板不同参数（张宇同题型数变式）→ 抽象为 `family{template_text, param_axis}` → **自动可生成器化**：一次人工审模板，换来无限的合法变体题——这直接桥接我们的生成器总线（family 是 generator 的逆向产物）。

### 3.3 冲突处理（同题多答案或答案打架）

按质证次序仲裁：`auto_verified > 人工复核 > cross_checked 多数票 > unverified`；仲裁历史进 provenance.relations（争议不删，降 weiß 级留档——教辅勘误是常态不是事故）。

---

## 4. 验证分级（verify 不只对答案，对整条训练价值门）

进入练习池的额外过滤（审核门三问）：

```
G1 题型可判？        choice/blank → 判定器接得上（answer_type 有解）/ 解答题 → self_report 通道
G2 页码级出处        无出处不进池（可能是 OCR 幻觉/网络拼接）
G3 考纲符合？        kid 标注存在且 exam 作用域匹配（用基底的 exam 字段过滤数一/二/三）
```

三问全过才进 `practice_pool`；练习池**永远只是 provenance 库的一个视图**，不是数据本体。

## 5. 属于数据工程的「机械段」工具面（规划，含决策人已有先例）

| 段 | 工具方向 | 决策人已有系统 |
|---|---|---|
| ① 源摄取 | PDF 拆章 / 目录切分 / 扫描件清洗 | 他的《大话计算机》流程与 ingest.py 同证据——**本设计对其进行「数学扩展」，不是重造** |
| ② 公式 OCR | **MinerU4.0 standard（首选）/ Chandra 2（A/B）/ 现有 Marker 作对照组**——详见 §8（2026-09-17 追加；§7 开放题中「先试 pix2text」已作废） | 决策人已有 RTX 5060 + Marker 工作流残留可作对照线 |
| ③ 对拍 | 与墨题库/官方答案的字符串+数值对拍 | exact.py 直接复用（数值容差与 Fraction 判等） |
| ④ 标注 | 68 考点树受控词表 → ⓛ LLM 提议 → 置信门 → 人确认 | 评审链验证过的 tutor 知识树直接复用为词表 |
| ⑤ 打包 | `data/banks/<bank>-vN.json`（含 provenance+schema_version） | gen_bundles 打包器复用（生成器与 OCR 题库走同一灌库路径） |

**工程量锚（诚实）**：决策人说「机械但量大」——按《大话计算机》管道经验，一本书的章节切+清洗约 1~2 晚； OCR 公式段的抽检才是真成本（按 10% 抽检人工过目）。给出阶段性预期：**第一本完成端到端时可能就要 1~2 周**（含管线调试），后续每本边际成本下降明显。这符合他「最长时间花在数据」的判断，跟他考研主线无冲突——**管线打第一条流水线在 Phase 3 之后再启动**，避免跟我推荐的主线（先把练题闭环跑起来）抢时间。

## 6. 题库的长期演进纪律（决策人要的「不断更新迭代」）

1. **bank 不可变 + 追加制**：`banks/<name>-vN.json` 只增版不改写；attempts 引用 qid 永不解引用失败（因为已入池的题被改版本时旧 qid 保留）
2. **变更走重 command**：改一个答案/勘误 = 发新版本 bundle + provenance.revision 记录（带原因），不是原地改
3. **词表演进**：kp 词表原则上随基底 68 树同步；新增考点点位需走 contracts 变更（树+题库+标注三者同 commit 变更——契约纪律的同一条）
4. **审校队列人工节奏**：每天的 OCR 草稿进审校队列，**决策人自己在练题系统里被考到的题即人工审核的最小闭环**（做题时发现题错 = 顺手报错 = 数据管线被用户侧反哺——这是这个项目独有的飞轮）

## 7. 开放问题（决策人后续拍板）

1. 第一本 OCR 的书选什么？建议从**教材课后题**起（《高等数学》/ 《线性代数》同济第六版习题分布均匀、排版好、答案分开）——「机械顿悟」风险最低
2. OCR 引擎选型：pix2text（开源，准中文教材）先试；若都不行，扫描 +人工输入的成本 Model 需另算
3. 每天审批校多少题的节奏（建议 10~20/天，跟着练题闭环走——数据管线成为练题的副产品而非抢跑者）
4. provenance 的 book 字段是否接 ISBN/书号管理（规划期不需要，先散列字符串）
5. 竞赛源（CMC-SpeedRun PDF）与考研线是否共池（建议**共池但打 source 标签**，练习池按主副线过滤来出题）

## 8.（2026-09-17 追加）OCR 引擎选型核验 —— 决策人旧方案已落伍，有硬证据

> 触发：决策人提交其 2026-06 的五轮工具迭代笔记（Marker 胜出，33 分钟 CPU 全本《吉米多维奇》），要求社区核验时效性。
> 方法：双路子代理（工具演进核验 / 社区口碑）+ 主会话 OmniDocBench 榜单实测解析 + PyPI 版本时间线。证据留档：`pdf-tool-recheck-2026/`、`ocr-survey/`、`math-practice-survey/raw/omnidocbench.md`。

### 8.1 三链证据交汇的裁决

**「Marker 方案已落伍」成立，且比想象更彻底——不仅成绩落gages，连用法都变了：**

1. **基准位次（OmniDocBench v1.7，2026-04-30 增 296 难例页、公式占比提高；主会话独立解析全表 35 行）**：
   - Marker 78.44，全榜 35 位中**倒数第二**；公式 CDM 85.24 vs 当前专用小 VLM 榜首 97.53 ——公式维度差一整档
   - 同为 pipeline 类的对照：MinerU-Pipeline 86.47（榜首段差 8 分）
   - 公平性注：olmocr-bench 上 Marker 自报 76.0%（两类基准口径不同；OmniDocBench 含公式 CDM 专项，与本题场景更相关）
2. **形态变化（PyPI 实证）**：`marker-pdf` 2.0.0（2026-07-20）依赖头即 `anthropic`——v2.0 重写为「本地推理服务器」：**GPU 平衡模式需 vLLM + Docker + NVIDIA Container Toolkit，CPU 模式改走 llama-server**；surya 换成 650M OCR-VLM（另：`magic-pdf` 包名停于 1.3.12 / 2025-05，继任者即 `mineru`），学生笔记里 `SURYA_DEVICE=cpu marker_single` 的一键直调流程**已不存在**
3. **旧坑的正反面**：MinerU 4.0.0（2026-09-16 发布，PyPI 实测）— base 包 = ONNX(CPU) + llama.cpp(Vulkan)，**不强制 torch/paddle**，正面修复学生五轮踩坑链；安装矩阵含显存档位（standard 档 8GB VRAM 可用 → RTX 5060 足够）

### 8.3 选型定案（三轨并行 + 硬件闸门 + bug 回归测试；双路子代理分歧的裁定）

> 分歧记录（诚实）：A 路（工具核验）判「MinerU 4.0 首选、Chandra 2 做 A/B」；B 路（社区口碑）判「Chandra 2 首选、MinerU 备选」，理由是它在 2026-07~09 挖到 MinerU 的公式 bug 连续流。两方证据都成立，**分歧的根源是评估轴不同**（A 路重安装与管线工装，B 路重公式精度）。裁定方式：不选边，改三轨并跑 + 硬件闸门。

| 轨道 | 引擎 | 角色 | 为什么是它 | 前置闸门 |
|---|---|---|---|---|
| **骨干** | **MinerU 4.0 standard** | 全书批量转换主力 | 8GB VRAM 档位官方有表（5060 达标）；base 包 ONNX+llama.cpp **不依赖 torch/paddle**（Blackwell 架构安全）；MinerU2.5-Pro 权重 95.75/公式 97.45；管线工装最厚（文档库/LaTeX 导出/分层解析/agent 技能） | ⚠️ **先跑 4 条已知 bug 复现页**：#5479 行内公式重复符号 / #5383 表格公式漏识 / #5289 公式编号多括号 / #5275 表格公式导出裸 LaTeX。全过→骨干成立；命中→该页型交专轨 |
| **公式专轨** | **PaddleOCR-VL-1.6（官方 GGUF）** | 公式密集页与骨干 bug 命中的页型 | **公式 CDM 榜首 97.53** + 0.9B + **GGUF 走 llama.cpp**（不碰 torch）——硬件适配与公式适配同时最优 | 待验：GGUF 在 5060 上的实测吞吐 |
| **观察候选** | **GLM-OCR (1.3B, MIT) / TeleOCR (1.2B, Apache-2.0)** | 骨干与专轨都失手时的第三手 | 两者均 **8GB 可行**，许可证最干净；TeleOCR 为当前 Overall 榜首 | ⚠️ TeleOCR 今日(2026-09-17)刚上架，成熟度未验 |
| ❌ **出局**（曾拟"精度参照轨"） | **Chandra 2 (5.3B)** | —— | 官方有 "Chinese Math" 样例页、HN 口碑最佳，但： | **8GB 不适配**：5.3B BF16 ≈ **11GB 显存**（A 路实测判）；仅可走官方 playground 免费额度做困难页人工比对 |
| 对照组 | 现有 Marker 1.x 产出 | 只作对拍基线 | 已跑通全本，输出在手 | — |

**Chandra 2 的双重边界（许可证 + 硬件）**：代码 Apache-2.0，但**权重是 modified OpenRAIL-M**（个人/研究免费、商业自托管需授权、不得与官方 API 竞争）；且 **5.3B / BF16 ≈ 11GB 显存，超出决策人 8GB 上限**。结论：个人自用许可无忧，但**本机跑不动**——留在案作将来换硬件的候选，不作为当前管线组件。

**仍排除**（证据见双路报告）：DeepSeek-OCR（2026-01 起停更 + vllm-0.8.5 钉死 + **Blackwell sm_120 幻觉循环 issue #339 未修**——决策人 5060 正属此架构）；olmOCR（linearized 纯文本输出，架构上不适配 Markdown+LaTeX）；Pix2Text（停在 2025-07 V1.1.4）；dots.ocr（已改名 dots.mocr，HF 路径 OOM/flash-attn 冲突）。

**20 页样书实验协议（验收即实验，不以榜单替代实拍）**：
- 选页：从《吉米多维奇》抽 20 页 = 5 页嵌套分式 + 5 页积分上下限 + 5 页表格/多栏 + 5 页普通题
- 三跑：MinerU4.0(standard) / PaddleOCR-VL-1.6-GGUF /（显存允许则）Chandra 2(hf)  + 对照组 Marker 旧输出
- 量尺：①**公式转写正确率**（人工逐字符对数，每工具抽 ≥30 处）②结构块完整率（标题/表格/公式行）③耗时与显存峰值
- 判据：公式正确率 ≥97%（对齐榜单档位）且无系统性错型 → 该工具进骨干/专轨
- 留档：原始输出进 `references/ocr-ab-<date>/`（**含版权内容，不进开源仓**）

### 8.4 一条纪律（月更赛道的保险丝）

OmniDocBench 每 1-2 月刷新一榜（本榜 2026-09-11 已加 TeleOCR/OvisOCR2/Unlimited-OCR 三个新冠军候选）——**选型以「拍球时点的榜单 + 实拍对拍」为准，不背任何一次锚定结论超过 90 天**。本节 v1.0 证据日期 2026-09-17，若 >90 天后启动 Phase 3 管线，**先重刷本节榜单再动手**。
