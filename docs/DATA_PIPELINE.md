# 数据管线设计 v1（DATA_PIPELINE）

> 定位：把「多本权威书的 OCR 草稿」融合成「高质量、可演进、带出处」的题库资产。
> 本文是设计文档（规划期，零代码）；它与练题系统**只通过 contracts/ 共享契约**，是平行工程不是耦合件
> 决策人的原始判断（本管线的设计出发点，已全部吸收）：
> ① 数据 > 一切（垃圾进垃圾出）② 提取是机械但量大的活 ③ 真技术含量在多源融合 ④ 题库要长期迭代 ⑤ 公开数据集不入池（可作交叉校验参考）

## 1. 管线总览（六段流水线，每段有验收门；LLM 只出现在标 ⓛ 的位置）

```
① ingest 源摄取      书/PDF/教材 → 原始素材（按章分节，frontmatter 记出处）
② segment 题目切割   题干 / 解答 / 易错点 分离（启发式 + 人工抽检）
③ formula 公式规范化 LaTeX 清洗 + 宏展开 + 等价形式标注
④ annotate 知识点标注 ⓛ LLM 提议 → 置信度 → 人工确认（受控词表=68 考点树）
⑤ verify 答案验证    分级门（见 §4）——这是数据侧的 fail-closed
⑥ fuse 融合/去重     跨书同题识别 + 参数化模板识别 + 出处聚合 → bank
```

**纪律**：LLM 永不出现在 ⑤ 的判定链路（N3 的数据侧镜像）。ⓛ 只出现在④，且必经人工确认才算落库。

## 2. 最重要的设计决策：**验证分级门**（verify 的四档）

这是把「垃圾进垃圾出」变成工程问题的全部所在。每道题带**验证状态**，入池规则如下：

| 级别 | 判定方式 | 允许进入 | 备注 |
|---|---|---|---|
| `auto_verified` | **exact.py 等 CAS 代码可判定**（或生成器自产） | ✅ 练习池 | 质量最高，MVP 主力；与练题系统 answer_type 同构 |
| `cross_checked` | ≥2 个独立来源答案一致（OCR+墨题库对拍 / 多书对拍，含参数一致性） | ✅ 练习池（标注 cross） | 需要融合层做参数抽取比对 |
| `human_confirmed` | 决策人读过解析、手工确认答案 | ✅ 练习池 | 解答题的主要通道 |
| `unverified` | 仅 OCR 未复核 | ❌ 只进**审校队列**，不进练习池 | OCR 的默认落点——垃圾进不了池子 |

> 状态机的关键性质：**只能升级、不可降级、不可跳级**（unverified → verified 两条路：auto 或 human；任何已确认题被上游复核降级需记录 ADR）。

## 2.A Provenance（出处追踪）—— 题库能长期演进的免费的纪律

每条题目除了 qa 契约字段（ARCHITECTURE §3.1），携带：

```
provenance:
  book:        书名/作者/版次（受控名著表，防拼写漂移）
  page:        页码（OCR 段落锚点）
  ocr:         [引擎, 版本, confidence]
  segment:     切割判定依据（题号匹配/正则锚点），供回溯原文
  verified:    见 §2 四级状态 + verifier + ts
  relations:   dup_group（同题跨书） / family（参数化同模板） / cross_refs
```

**一票否决的边界（承接既有红线）**：带 provenance 的原始 OCR 数据**永不上传开源仓库**——开源仓里只放「我方生成的题目 xor 用户自备 custom_json」；OCR 资产停在本地/私有备份。

### 2.B 答案获取优先级（CAS-first，2026-09-19 追加）

> 触发：决策人提出「只要题目提取完全，答案尽力即可，反正以后接强 agent」。**效率判断正确**（解答区正是 OCR 最烂处，题目只有 1-3 行），**但理由必须替换**——答案可以不来自书，但不能不可验证。

**四级来源，优先级从高到低**：

| 级 | 来源 | 生成方式 | 强度 | 进练习池？ |
|---|---|---|---|---|
| **L1** | **CAS 独立计算 + 与书答案对拍** | `core/exact/`（线代：行列式/秩/逆/矩阵/方程组/特征值/二次型）或 sympy（高数：极限/导数/积分/级数） | **最强：双源一致** | ✅ 最优来源 |
| **L2** | 仅书上答案（CAS 不可算：证明题、带参讨论） | 人工录入/OCR 校对 | 强（人写、可复核） | ✅ 标 `cross_checked` |
| **L3** | 书无答案 且 CAS 不可算 | —— | 弱 | ⚠️ 人工确认，或标 `self_report`（使用者自评） |
| **L4** | **仅 LLM/agent 生成** | —— | **最弱（单源未校验）** | ⛔ **永不进判分链路**；仅可用于讲解、提示、辅助人工 |

**关键等式**：书上答案的价值 = **CAS 的独立对拍源**，而非答案本身。两边一致 → 该题才可进池。

**覆盖率预估（决定这条路可行）**：线代教材习题 **CAS 可算 ≈60-80%**；高数 ≈50-70%；证明/推导类 20-30% 不可算。→ **多数题目的答案质量的担忧可以消解：机器算得比 OCR 准。**

**由此反转的一条关键路径**：CAS 需要题目作为输入 → **题目必须提取为正确的 LaTeX**。**题目提取质量（而非答案提取质量）成为数据管线的唯一关键路径**——这与决策人「题目优先」的方向一致，只是原因从「反正有 agent」改为「答案由机器算，题目是命门」。

**与 N3 的关系**：本条是 N3（判分必须精确、LLM 永不进判定链路）在**数据侧的延伸**——不仅判分不许 LLM，**判分所依据的标准答案也不许仅来自 LLM**。


### 2.C 验证闸门：让 agent 大量生产答案，但必须过闸（2026-09-19，实证后追加）

> 实证背景：就「模型能否直接给出标准答案」做了自测——**13 道线代题（含 2 道陷阱题：几何重数 vs 代数重数、重复特征值不保证可对角化）全部答对**。
> **但同期验证层出了 6/13 假阴性**（字符串比对 vs 规范型比对，答案全对而判错）。
> 结论：**生成已不是瓶颈，等价判定与验证才是。** 故把 agent 的定位从「答案生产者」改为「**验证加速器**」，并设五道闸门。

| 闸门 | 做法 | 治什么 |
|---|---|---|
| **G1 多路一致性** | 同题 N 次（不同提示/温度）或跨模型，结果一致才采信 | 单次采样错误 |
| **G2 CAS 独立计算** | `core/exact/`（线代）/ sympy（高数）算一遍 | 提供**可判定性**（decidable），而非"大概对" |
| **G3 回代验证** | 解代回原方程 / 矩阵等式（如 A·v = λv、A·A⁻¹ = I） | **与被求解者无关的正确性证明** |
| **G4 符号等价判定** | `simplify(候选答案 − 对拍答案) == 0`（**禁止字符串比对**） | 等价形式的不可判定（实证：字符串比对 6/13 假阴性） |
| **G5 书上答案对拍** | 与《习题全解指南》类成册解析比对 | 独立第三方源 |

**采信规则**：多源一致 → `verified`；单源（含仅 LLM）→ `unverified`，**只进探索区，不进判分池**。

**agent 的定位**：不是当标准答案，而是**验证加速器**——快速产出候选 + 生成验证脚本（回代式/等价式）+ 判读失败原因（是它错了、题目 OCR 错了、还是等价判定写错了），把大批 `unverified` 批量转 `verified`。**吞吐用在最难的地方（验证），而不是最容易出错的地方（直接当标准）。**

**两个必须记住的失败模式**：
1. **低温消除随机性，不消除系统性错误**。`temperature=0` 会让同一个坑稳定复现，成片污染且每道都"看起来对"。
2. **不可检测性才是要害**：模型全对时你无法区分「全对」与「错一题」，除非有独立验证路径——判卷器只给分表，不给"这里可能错了"的提示。

**待测量（用数据收敛分歧，不靠立场）**：抽 100-200 道带答案的题 → agent 作答 → 与书答案 + CAS 三方对比 → 测 ① 真实错误率 ② 错误集中的题型 ③ **错误中可被自动检出的比例**。此 harness 为长期资产（换模型/调提示词/换框架均可复测）。

## 3. 融合（fuse）的三类判定规则 —— 这里是技术主战场

### 3.1 同题跨书（dup_group）

判据（优先级降序）：① **数学内容指纹**：规范化后的 stem 等价（公式规范化后 hash；公式树不比特串——`\dfrac` vs `\frac` 视为同）② 参数一致（数值题比对全部出现数字集合）③ 结论/答案等价。
处理：合并 provenance（多书互证 → 升 cross_checked）、保一条 canonical（选解析最完整者），其余指向 canonical。

### 3.2 参数化同源（family）——**这是融合最有价值的一步**

同一模板不同参数（张宇同题型数变式）→ 抽象为 `family{template_text, param_axis}` → **自动可生成器化**：一次人工审模板，换来无限的合法变体题——这直接桥接我们的生成器总线（family 是 generator 的逆向产物）。

### 3.3 冲突处理（同题多答案或答案打架）

按质证次序仲裁：`auto_verified > 人工复核 > cross_checked 多数票 > unverified`；仲裁历史进 provenance.relations（争议不删，降 weiß 级留档——教辅勘误是常态不是事故）。

## 4. 验证分级（verify 不只对答案，对整条训练价值门）

进入练习池的额外过滤（审核门三问）：

```
G1 题型可判？        choice/blank → 判定器接得上（answer_type 有解）/ 解答题 → self_report 通道
G2 页码级出处        无出处不进池（可能是 OCR 幻觉/网络拼接）
G3 考纲符合？        kid 标注存在且 exam 作用域匹配（用基底的 exam 字段过滤数一/二/三）
```

三问全过才进 `practice_pool`；练习池**永远只是 provenance 库的一个视图**，不是数据本体。

## 5. 属于数据工程的「机械段」工具面（规划，含决策人已有先例）

| 段 | 工具方向 | 决策人已有系统 |
|---|---|---|
| ① 源摄取 | PDF 拆章 / 目录切分 / 扫描件清洗 | 他的《大话计算机》流程与 ingest.py 同证据——**本设计对其进行「数学扩展」，不是重造** |
| ② 公式 OCR | **MinerU4.0 standard（首选）/ Chandra 2（A/B）/ 现有 Marker 作对照组**——详见 §8（2026-09-17 追加；§7 开放题中「先试 pix2text」已作废） | 决策人已有 RTX 5060 + Marker 工作流残留可作对照线 |
| ③ 对拍 | 与墨题库/官方答案的字符串+数值对拍 | exact.py 直接复用（数值容差与 Fraction 判等） |
| ④ 标注 | 68 考点树受控词表 → ⓛ LLM 提议 → 置信门 → 人确认 | 评审链验证过的 tutor 知识树直接复用为词表 |
| ⑤ 打包 | `data/banks/<bank>-vN.json`（含 provenance+schema_version） | gen_bundles 打包器复用（生成器与 OCR 题库走同一灌库路径） |

**工程量锚（诚实）**：决策人说「机械但量大」——按《大话计算机》管道经验，一本书的章节切+清洗约 1~2 晚； OCR 公式段的抽检才是真成本（按 10% 抽检人工过目）。给出阶段性预期：**第一本完成端到端时可能就要 1~2 周**（含管线调试），后续每本边际成本下降明显。这符合他「最长时间花在数据」的判断，跟他考研主线无冲突——**管线打第一条流水线在 Phase 3 之后再启动**，避免跟我推荐的主线（先把练题闭环跑起来）抢时间。

## 6. 题库的长期演进纪律（决策人要的「不断更新迭代」）

1. **bank 不可变 + 追加制**：`banks/<name>-vN.json` 只增版不改写；attempts 引用 qid 永不解引用失败（因为已入池的题被改版本时旧 qid 保留）
2. **变更走重 command**：改一个答案/勘误 = 发新版本 bundle + provenance.revision 记录（带原因），不是原地改
3. **词表演进**：kp 词表原则上随基底 68 树同步；新增考点点位需走 contracts 变更（树+题库+标注三者同 commit 变更——契约纪律的同一条）
4. **审校队列人工节奏**：每天的 OCR 草稿进审校队列，**决策人自己在练题系统里被考到的题即人工审核的最小闭环**（做题时发现题错 = 顺手报错 = 数据管线被用户侧反哺——这是这个项目独有的飞轮）

## 7. 开放问题（决策人后续拍板）

1. 第一本 OCR 的书选什么？建议从**教材课后题**起（《高等数学》/ 《线性代数》同济第六版习题分布均匀、排版好、答案分开）——「机械顿悟」风险最低
2. OCR 引擎选型：pix2text（开源，准中文教材）先试；若都不行，扫描 +人工输入的成本 Model 需另算
3. 每天审批校多少题的节奏（建议 10~20/天，跟着练题闭环走——数据管线成为练题的副产品而非抢跑者）
4. provenance 的 book 字段是否接 ISBN/书号管理（规划期不需要，先散列字符串）
5. 竞赛源（CMC-SpeedRun PDF）与考研线是否共池（建议**共池但打 source 标签**，练习池按主副线过滤来出题）

## 8.（2026-09-17 追加）OCR 引擎选型核验 —— 决策人旧方案已落伍，有硬证据

> 触发：决策人提交其 2026-06 的五轮工具迭代笔记（Marker 胜出，33 分钟 CPU 全本《吉米多维奇》），要求社区核验时效性。
> 方法：双路子代理（工具演进核验 / 社区口碑）+ 主会话 OmniDocBench 榜单实测解析 + PyPI 版本时间线。证据留档：`pdf-tool-recheck-2026/`、`ocr-survey/`、`math-practice-survey/raw/omnidocbench.md`。

### 8.1 三链证据交汇的裁决

**「Marker 方案已落伍」成立，且比想象更彻底——不仅成绩落gages，连用法都变了：**

1. **基准位次（OmniDocBench v1.7，2026-04-30 增 296 难例页、公式占比提高；主会话独立解析全表 35 行）**：
   - Marker 78.44，**全榜 35 位中末位（第 35 名，垫底）**；公式 CDM 85.24 vs 当前专用小 VLM 榜首 97.53 ——公式维度差一整档
     > ⛔ **更正（2026-09-19 原始 HTML 逐行复核）**：此处原写「**倒数第二**」——**错误**。直接解析 `omnidocbench.md` 的 **36 个 `<tr>`**（=1 表头 + 35 模型）确认 Marker 为**第 35 名即全榜最末**，且各维度全面垫底（TableTEDS 65.77 倒数第一、ReadOrder 0.243 倒数第一、TextEdit 0.157 倒数第一）。方向不变（结论更强化），但数字已校准。
   - 同为 pipeline 类的对照：MinerU-Pipeline 86.47（榜首段差 8 分）
   - 公平性注：olmocr-bench 上 Marker 自报 76.0%（两类基准口径不同；OmniDocBench 含公式 CDM 专项，与本题场景更相关）
2. **形态变化（PyPI 实证）**：`marker-pdf` 2.0.0（2026-07-20）依赖头即 `anthropic`——v2.0 重写为「本地推理服务器」：**GPU 平衡模式需 vLLM + Docker + NVIDIA Container Toolkit，CPU 模式改走 llama-server**；surya 换成 650M OCR-VLM（另：`magic-pdf` 包名停于 1.3.12 / 2025-05，继任者即 `mineru`），学生笔记里 `SURYA_DEVICE=cpu marker_single` 的一键直调流程**已不存在**
3. **旧坑的正反面**：MinerU 4.0.0（2026-09-16 发布，PyPI 实测）— base 包 = ONNX(CPU) + llama.cpp(Vulkan)，**不强制 torch/paddle**，正面修复学生五轮踩坑链；安装矩阵含显存档位（standard 档 8GB VRAM 可用 → RTX 5060 足够）

| **S 级** | PaddleOCR-VL-1.6 | 0.9B | 96.34 | **97.53** | 公式 CDM 榜首；官方 GGUF 可 llama.cpp 跑 |

### 8.3.1 运行档追加：**低占用 GPU（base 档 + Vulkan）**（2026-09-19，决策人新约束；同日二次修订）

**新输入**：决策人桌面为 **KDE Plasma / Wayland + KWin 直接渲染**，桌面常驻占用 **~1.1GB 显存 / 40W / 64°C**；历史故障为「显存紧张 + 功耗尖峰 → 显卡杀死桌面进程 → 系统全线崩溃」。
**决策人澄清（重要）**：「**也不是别碰 GPU，GPU 算得快呀；只不过不激进地跑，让 GPU 占用小一点，应该也不会有问题**」。
→ 故否决本人初稿的「CPU-only」极端方案（矫枉过正），改为 **GPU 加速但严控占用**。

**MinerU 官方硬件矩阵（`ocr-survey/raw/mineru-readme.md` 原文，实测取证）**：

| Tier | Model engines | 模型下载 | 最低 RAM | Accelerator |
|---|---|---|---|---|
| `basic` | ONNX | ~0.8 GB | 2 GB | 无（CPU 可用） |
| `basic` | PyTorch | ~0.8 GB | 8 GB | GPU/MPS 推荐 |
| **`standard`/`advanced`** | **ONNX + llama.cpp** | **~2 GB** | **8 GB** | **CPU 可用，推荐 Vulkan** ← ⭐ |
| `standard`/`advanced` | PyTorch + llama.cpp | ~2 GB | 16 GB | 必须 GPU，8GB+ VRAM |
| `standard`/`advanced` | PyTorch + vLLM/lmdeploy | ~3 GB | 16 GB | 必须 GPU，8GB+ VRAM |

**官方「按硬件推荐」表原文**：

| Hardware | Recommended startup tier | Model engines | Extra |
|---|---|---|---|
| Linux/Windows with **NVIDIA GPU and 8GB+ VRAM** | `standard` | **PyTorch + vLLM/lmdeploy** | **`full`** |
| **Linux/Windows with modern iGPU** | `standard` | **ONNX + llama.cpp** | **`(base)`** ← ⭐ |
| Linux/Windows w/o modern accelerator | `basic` | ONNX | `(base)` |

> ⚠️ **反直觉但关键**：按硬件规格，官方会给他推荐 `full`（8GB+ VRAM 那行）——**而那正是会崩他桌面的组合**（PyTorch + vLLM 需独占 8GB+ VRAM）。
> **我们故意按「modern iGPU」那一行装**：`(base)` extra = **ONNX(CPU) + llama.cpp(Vulkan)**，模型仅 ~2GB，
> **VRAM 需求从 8GB+ 降到 ~2GB，与桌面 1.1GB 并存仍余 4GB+ 余量**。
> **官方推荐 ≠ 适合本机。这条偏离是有意的，理由成立且已留档。**

**结论：定案（§8.3 三轨）不变；运行档 = `(base)` extra + `standard` tier + Vulkan 走 GPU。**

## 9. 二次校验设计（OCR 错误检测，2026-09-19 追加）

> 触发：决策人提出「是否安排第二个模型/工具做第二遍校验」。**方向正确，但形态必须是「分层检测 + 定点复核」，而非「第二引擎全量重跑」。**

### 9.1 为什么不做全量双跑（三条硬理由）

1. **同源偏差**：两个 OCR 对同一处模糊笔迹常犯同一个错 → 全量双跑是双倍成本换假安心。
2. **第二引擎通常更弱**：显存/时间约束下不可能同时跑两个顶级模型，弱输出无裁判资格。
3. **无真值基准**：两个输出并列时无法判定谁对 → **引擎投票只能当 triage 线索，不能当裁决。**

### 9.2 三层闸门（越靠前越便宜）

| 层 | 手段 | 需第二模型 | 覆盖 |
|---|---|---|---|
| **L0 结构/自洽闸**（免费） | LaTeX 语法校验；**渲染回环**（抽出 LaTeX → 渲回图片 → 与原扫描区域比对 diff）；页文本量异常；题号连续性；符号表校验 | ❌ | 结构级、布局级、漏行 |
| **L1 语义对拍闸**（最强，免费） | **CAS 计算答案 vs 书上答案**；回代验证（A·v=λv、A·A⁻¹=I、解代回原式） | ❌ | 语义级（负号/区间/上下标） |
| **L2 定点复核**（贵但量小） | 第二引擎/模型**仅跑被 L0/L1 标记的条目** + 人工比对 | ✅ | 残留疑难 |

### 9.3 核心机制：用答案当题目的错误检测器

```
题目 OCR → CAS 独立算答案 → 与书上答案对拍
                             ├─ 一致 → 题目与答案双源确认 ✅
                             └─ 不一致 → 必有一错 → 进审校队列 ⚠️
```

**任何 OCR 错误（丢负号/根号范围错/丢上标）几乎必然使 CAS 答案偏离书上答案** → 得到一个**逐题、语义级、零额外成本**的校验器，且**同时校验题目与答案两侧**。
（这正是 §2.C 的 G2+G5 闸门在管线层的复用。）

### 9.4 错误分类 × 检测器对照表

| 错误类 | 典型形态 | 检测器 | 成本 |
|---|---|---|---|
| **结构级** | `\frac{a}{b}`→`a/b`、`x^2`→`x2`、矩阵括号丢失、根号范围错 | LaTeX 解析合法性 + **渲染回环图像比对** | 低 |
| **语义级** | 负号丢失、区间开闭 `(` vs `[`、上下标错位 | **CAS 答案 vs 书上答案** + 回代 | 低 |
| **符号级** | `x`/`×`/`χ`、`α`/`a`、`l`/`1`、`O`/`0` | 双引擎差异高亮 + 字符置信度（若有） | 中（L2） |
| **布局级** | 跨栏串行、**题号错配**（题干与答案张冠李戴） | 题号连续性 + 页文本量异常 + 阅读顺序校验 | 极低 |
| **漏行/漏页** | 整段静默丢失 | 页字符数分布异常 + 与前後页对比 | 极低 |

**实证（2026-09-19，在无第二个模型的情况下）**：对 `概率习题全解`（299 页）跑 L0 检测器 →
- **文本量异常偏低页 4 页**（p121 仅中位 22%、p208 15%、p216 13%、p185 33%）→ 疑漏行/残页
- 题号连续性：417 个可识别题号中 **90 处跳号**（噪声较大，只作线索，不作裁决）
- 结论：**免费检测器已能圈出 1-2% 的可疑页**，人工只需复核这部分。

### 9.5 引擎配对（供 L2 使用）

| 角色 | 引擎 | 说明 |
|---|---|---|
| 主力 | **MinerU 4.0 standard** | §8.3 骨干轨 |
| 公式专轨 / 复核器 | **PaddleOCR-VL-1.6-GGUF** | 不同家族 → 错误去相关 |
| **免费第三独立源** | **本批 PDF 自带的文字层** | 公式全坏但散文/数字尚可，且**藏有结构骨架（章节/题号/页码）**；家族不同 → 可做 L0 第三信号（如文字层 `sin x` vs OCR `cos x` → 冲突标记） |

### 9.6 纪律与预算

- **校验产出 flag，不产出 truth**：未通过的题**不被"改对"，而被标记** `needs_review`，进审校队列 → 由**决策人做题时顺手确认**（数据飞轮）。
- **人工预算**：L0/L1 自动 flag 后，人工仅需处理 **5-15%** 条目 → 2277 页从「两个月」压到「一两周」。**这就是"先建检测器、而不是先跑第二个模型"的理由。**
- 与既有契约一致：本条是 `§2` 四级验证（auto/cross/human/unverified）与 `§2.C` 五道闸门在**管线层**的执行设计。


### 9.7 降级决策：懒惰纠正路线（2026-09-19 第二轮收敛，决策人主张 + 规划方认可）

决策人提出「OCR 正确率已足够好，不必为少量错误投入大量精力；做到那道题时再纠正，模型可直接修」。
**规划方认可其 YAGNI 判断**（对个人工具，全量预校验属过度工程），故对 §9.2 三层闸门做如下**降级**：

| 保留（必需） | 砍掉/延后（按触发条件启用） |
|---|---|
| ✅ **Provenance 出处锚点**（`book / page / 区域`）——**懒惰纠正的命门**：没有它，做题时发现坏题只能删、无法修（OCR 已毁掉原文，且模型修复也需原页扫描图作依据） | ❌ **渲染回环**（LaTeX 渲回图片 diff） |
| ✅ **练习界面「报错」按钮**（一键写 `qid + 原因 + ts` 入修复队列）——把「到时候再纠正」从口号变成机制 | ❌ **L2 双引擎定点复核** |
| ✅ **`suspect` 标记**：CAS 答案 ≠ 书上答案 → 标记（**成本≈零**，两侧数据本就都有；不需遇到该题即可捞出可疑项） | ❌ **全量预校验**（L0 全套 / L1 批量跑） |

**触发条件（写死，防遗忘）**——满足任一条即启用被延后的 L0/L1/L2：
1. 真实「报错率」> **5%** 的已做题（即每 20 道题就有 1 道被报坏）；
2. 累计修复耗时 > **30 分钟/月**；
3. 题库准备**公开分发**（blast radius 从"个人"变成"公众"）。

**已知盲区（诚实记录）**：不会被调度引擎选中的坏题将长期潜伏，且使用者无从判断题库整体质量。对个人工具可接受（开源的是**代码**，题库数据不外发）；一旦演变为公开题库服务，此盲区立即升级为阻塞项（触发条件 3）。

**估算（非实测，Phase 3 校准）**：单题正确率 ≈ (单公式准确率)^(该题公式/数字个数)。按 0.98^4 ≈ 0.92 → 约 8% 题目带错；按乐观 0.99^4 ≈ 0.96 → 2000 题池仍有数十道带错。故「那点错误」的实际量级是「几十次几分钟」，而**每次可修的前提仍是 provenance 存在**。

**模型直接纠正的前提（回应决策人「模型应该可以直接纠正」）**：成立，但同样依赖 provenance——须把**原页扫描图**喂给模型，它才能判别 `x2` 是 `x^2` 还是 `x_2`。有锚点 → 数十秒；无锚点 → 只能猜或删题。
